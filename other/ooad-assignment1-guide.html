1. Lab 02: Use Case Diagrams

Complete UML Conventions & Symbols (Use Case Diagrams):
  • Actor: External entity (human or system) interacting with the system.
  • System Boundary: Box defining the scope of the system. Actors remain outside.
  • Use Case: Represents a functional requirement. Drawn as an ellipse.
  • Association: Solid line connecting an Actor to a Use Case they participate in.
  • Dependency (<<include>> / <<extend>>): Dashed arrow showing relationship between use cases.
  • Generalization: Solid line with hollow triangle. Inheritance between actors or use cases.

Exercise 1: Ticket Vending System

Question: The goal of this project is to provide a system for commuters to buy tickets. When a user arrives at the vending machine he or she can view the available bus routes with the destinations. The user can select one of the destinations. Then the vending machine calculates the price of the ticket based on the current location and shows it to the user. The user can input coins and currency bills into the machine. The machine can count the inserted amount and dispense the tickets and balance amount if there is any. The administrators of the system can view the available bus routes in order to add new destinations or delete or modify the existing destinations. If a new destination is added, the administrator should test the system by buying a mock ticket to the newly added destination. Buying a mock ticket is similar to the normal buying process but can skip the payment process if the administrator decides not to test the payment module.
Identified Users (Actors): Commuter, Administrator.
Explanation: The system boundary separates the Ticket Vending System from the users. The Commuter triggers the main buying process. "Buy Ticket" mandates payment processing and ticket dispensing, so we use <<include>>. "Test System" is an optional variant of buying a ticket for administrators, modeled with <<extend>>.

Exercise 2: Automated Vehicle Care System

Question: The goal of this project is to provide a system for vehicle owners to get vehicle cleaning and checkup services. The registration unit at the entrance automatically checks the number plate of the vehicle in order to check whether the owner is an existing customer to issue a care plan according to the type and the history of service turns of the vehicle. If the owner's details are absent then the machine will automatically recognize the type of the vehicle and ask the customer to enter the details. Once the customer submits the form, the care plan will be issued. A customer is always willing to do an exterior cleaning with wax polishing. However, the owners of public transport vehicles always do an interior cleaning and engine checkup additionally. The owners of off-road vehicles also can do an engine checkup if they want. After every successful completion of a caring step (ex. the exterior cleaning, interior cleaning or engine checkup, etc.) a technician marks the completed caring processes on the care plan issued to each customer at the entrance. At the exit point, a payment processing machine checks the care plan of the customer and issues an invoice. The customer can then pay with a prepaid card issued by the caring center. Then the machine will process the payment. If the vehicle is owned by a newly registered customer, then a 20% discount will be given in the process of payments. Further, a 10% discount will be given to the existing customers after every three service turns.
Identified Users (Actors): Vehicle Owner (General), New Customer, Existing Customer, Public Transport Owner, Off-road Owner, Technician, System.
Explanation: Generalization is used here to reduce clutter. New, Existing, Public Transport, and Off-road owners are specialized versions of the general "Vehicle Owner". This means any use case connected to "Vehicle Owner" (like Exterior Cleaning or Process Payment) is inherited by all of them.
Assumptions: The "System" acts as a secondary actor automating the registration and payment processes. Discounts are considered internal business logic handled within the "Process Payment" use case and do not need a separate use case bubble.

2. Lab 03: Activity Diagrams

Complete UML Conventions & Symbols (Activity Diagrams):
  • Initial Node: Filled circle. Start of the workflow.
  • Action/Activity: Rounded rectangle. Represents a single step.
  • Decision Node: Diamond. One input, multiple outputs (guarded).
  • Merge Node: Diamond. Multiple inputs, one output (rejoining flows).
  • Fork/Join Node: Thick bar. Splits (Fork) or syncs (Join) concurrent threads.
  • Swimlanes (Partitions): Divides diagram to show who is responsible for actions.
  • Final Node: Bullseye. End of the entire process.
  • Flow Final Node: Circle with an X. Ends a single path without ending the whole process.

Exercise 1: University Library System

Question: A university library provides a system that allows students to borrow books. A student can search for a book by title, author, or ISBN and select a book to borrow. Before issuing the book, the system checks the availability of the selected book. If the book is unavailable, the borrowing request is rejected. Otherwise, the system checks whether the student has any overdue books or unpaid fines. If the student has unpaid fines, the student must pay the fine before the borrowing process can continue. Once all conditions are satisfied, the system records the borrowing transaction and issues the book. A librarian can add new books, update book information, or remove books from the library catalogue.
Explanation: The flow handles two sequential conditional checks using decision nodes: Availability and Fines. If a fine is paid, it flows into processing the payment, and then merges back to the main issuing flow (Record Borrowing). The Librarian's separate tasks (adding/removing books) are omitted from this specific student-borrowing workflow as they are separate, distinct processes. 
        stateDiagram-v2
            [*] --> SearchBook
            
            state Student {
                SearchBook : Search for book
                SelectBook : Select book to borrow
                PayFine : Pay outstanding fine
                ReceiveBook : Receive book
            }
            
            state LibrarySystem {
                CheckAvailability : Check book availability
                CheckFines : Check overdues and unpaid fines
                ProcessPayment : Process fine payment
                RecordBorrowing : Record transaction
                IssueBook : Issue the book
                RejectRequest : Reject borrowing request
                NotifyUnavailable : Notify Book Unavailable
            }
            
            SearchBook --> SelectBook
            SelectBook --> CheckAvailability
            
            state if_avail <<choice>>
            CheckAvailability --> if_avail
            
            if_avail --> CheckFines : [Book Available]
            if_avail --> NotifyUnavailable : [Book Unavailable]
            NotifyUnavailable --> RejectRequest
            RejectRequest --> [*]
            
            state if_fines <<choice>>
            CheckFines --> if_fines
            
            if_fines --> PayFine : [Has Fines]
            if_fines --> RecordBorrowing : [No Fines]
            
            PayFine --> ProcessPayment
            ProcessPayment --> RecordBorrowing
            
            RecordBorrowing --> IssueBook
            IssueBook --> ReceiveBook
            ReceiveBook --> [*]

Exercise 2: Hospital Appointment Management System

Question: StarLab Hospital has implemented an online appointment management system that allows patients to book appointments with doctors. A patient logs into the system and searches for a doctor by specialty. After selecting a doctor, the patient requests an appointment. The system verifies whether the patient has a valid medical record. If the patient is new, the system creates a new medical record before continuing. Next, the system checks the doctor's availability. If no appointment slots are available, the patient may select another doctor or cancel the booking request. This process continues until an available doctor is selected or the patient cancels the request. Once an appointment slot is assigned, the system requests payment. If the payment is unsuccessful, the patient may retry the payment or cancel the appointment. After successful payment, the system confirms the booking, updates the doctor's appointment schedule and records the appointment in the patient's medical history. At the same time, the billing department generates a payment receipt while the notification service sends an appointment confirmation to the patient. The appointment booking process is completed once all these activities have finished.
Explanation: This diagram utilizes multiple swimlanes to clearly separate responsibilities. The critical UML convention applied here is the use of a Fork node (parallel processing) after successful payment and recording the appointment. The system must simultaneously trigger actions in three separate swimlanes: confirming booking, generating a receipt (Billing Dept), and sending a notification (Notification Service). These concurrent actions are brought back together using a Join node before terminating. 
        stateDiagram-v2
            [*] --> LogIn
            
            state Patient {
                LogIn : Log into system
                SearchDoc : Search for doctor
                SelectDoc : Select doctor
                ReqAppt : Request appointment
                SelectAnother : Select another doctor?
                MakePayment : Make payment
                RetryPayment : Retry payment?
            }
            
            state System {
                CheckRecord : Check valid medical record
                CreateRecord : Create new record
                CheckAvail : Check slot availability
                AssignSlot : Assign appointment slot
                ReqPaymentSys : Request payment
                ProcessPay : Process payment
                ConfirmBook : Confirm booking
                UpdateSched : Update doctor schedule
                RecordAppt : Record in medical history
            }
            
            state BillingDept {
                GenReceipt : Generate payment receipt
            }
            
            state NotificationService {
                SendConf : Send appointment confirmation
            }
            
            LogIn --> SearchDoc
            SearchDoc --> SelectDoc
            SelectDoc --> ReqAppt
            ReqAppt --> CheckRecord
            
            state if_rec <<choice>>
            CheckRecord --> if_rec
            if_rec --> CreateRecord : [No Record]
            if_rec --> CheckAvail : [Valid Record]
            CreateRecord --> CheckAvail
            
            state if_avail <<choice>>
            CheckAvail --> if_avail
            if_avail --> SelectAnother : [No Slots]
            if_avail --> AssignSlot : [Slot Available]
            
            state if_another <<choice>>
            SelectAnother --> if_another
            if_another --> SelectDoc : [Yes]
            if_another --> [*] : [No/Cancel]
            
            AssignSlot --> ReqPaymentSys
            ReqPaymentSys --> MakePayment
            MakePayment --> ProcessPay
            
            state if_pay <<choice>>
            ProcessPay --> if_pay
            if_pay --> ConfirmBook : [Success]
            if_pay --> RetryPayment : [Fail]
            
            state if_retry <<choice>>
            RetryPayment --> if_retry
            if_retry --> MakePayment : [Yes]
            if_retry --> [*] : [No/Cancel]
            
            ConfirmBook --> UpdateSched
            UpdateSched --> RecordAppt
            
            state fork_postpay <<fork>>
            RecordAppt --> fork_postpay
            fork_postpay --> GenReceipt
            fork_postpay --> SendConf
            
            state join_end <<join>>
            GenReceipt --> join_end
            SendConf --> join_end
            join_end --> [*]

Exercise 3: Online Food Ordering System

Question: An online food ordering system allows customers to order meals from registered restaurants. A customer browses the available restaurants and selects one. The customer chooses one or more food items and adds them to the shopping cart. After reviewing the order, the customer proceeds to checkout. The system calculates the total amount and prompts the customer to complete the payment. If the payment is unsuccessful, the customer may either try the payment again or cancel the order. If the customer chooses to retry, the payment process continues until the payment is successful or the order is cancelled. After a successful payment, the system creates the order then sends an order confirmation to the customer, and forwards the order details to the selected restaurant at the same time. The restaurant prepares the food. Once the food is ready, the restaurant informs the delivery service to assign a delivery rider. The assigned rider travels to the restaurant while the restaurant prepares the order for collection. After collecting the order, the rider delivers it to the customer. Once the customer confirms receipt of the order, the system updates the order status to Completed.
Explanation: This workflow highlights complex cross-lane interactions. It uses a loop for payment retries, controlled by decision nodes. Upon order creation, a fork is used to simultaneously notify the customer and forward details to the restaurant. Another fork/join pair is used when the restaurant prepares the collection while the rider travels. 
        stateDiagram-v2
            [*] --> BrowseRes
            
            state Customer {
                BrowseRes : Browse restaurants
                SelectRes : Select restaurant
                AddFood : Choose food & add to cart
                Checkout : Review & proceed to checkout
                Pay : Complete payment
                RetryPay : Retry payment?
                ConfirmReceipt : Confirm receipt of order
            }
            
            state FoodOrderingSystem {
                CalcTotal : Calculate total
                ProcPay : Process payment
                CreateOrder : Create order
                SendConfCus : Send order confirmation
                FwdDetails : Forward details to restaurant
                UpdateStatus : Update status to Completed
            }
            
            state Restaurant {
                PrepFood : Prepare food
                InformDel : Inform delivery service
                PrepColl : Prepare order for collection
            }
            
            state DeliveryService {
                AssignRider : Assign delivery rider
                Travel : Rider travels to restaurant
                Collect : Collect order
                Deliver : Deliver order to customer
            }
            
            BrowseRes --> SelectRes
            SelectRes --> AddFood
            AddFood --> Checkout
            Checkout --> CalcTotal
            CalcTotal --> Pay
            Pay --> ProcPay
            
            state if_pay <<choice>>
            ProcPay --> if_pay
            if_pay --> CreateOrder : [Success]
            if_pay --> RetryPay : [Fail]
            
            state if_retry <<choice>>
            RetryPay --> if_retry
            if_retry --> Pay : [Yes]
            if_retry --> [*] : [No/Cancel]
            
            state fork_order <<fork>>
            CreateOrder --> fork_order
            fork_order --> SendConfCus
            fork_order --> FwdDetails
            
            FwdDetails --> PrepFood
            PrepFood --> InformDel
            
            state fork_del <<fork>>
            InformDel --> fork_del
            fork_del --> AssignRider
            fork_del --> PrepColl
            
            AssignRider --> Travel
            
            state join_coll <<join>>
            Travel --> join_coll
            PrepColl --> join_coll
            
            join_coll --> Collect
            Collect --> Deliver
            Deliver --> ConfirmReceipt
            ConfirmReceipt --> UpdateStatus
            UpdateStatus --> [*]

3. Lab 04: Sequence Diagrams

Complete UML Conventions & Symbols (Sequence Diagrams):
  • Participant/Lifeline: Represents an object's existence over time (time flows downwards).
  • Synchronous Message: Solid line with filled arrowhead. Sender waits for a response.
  • Asynchronous Message: Solid line with open arrowhead. Sender does not wait.
  • Return Message: Dashed line indicating a reply back to the sender.
  • Activation Bar (Execution Spec): Thin rectangle on a lifeline showing when an object is actively executing a process.
  • Combined Fragment (Alt/Opt/Loop): Frame used to group messages for conditional logic or loops.

Exercise 1: Online Movie Ticket Booking System

Question: An Online Movie Ticket Booking System allows customers to book movie tickets. A customer searches for the movie "Spider-Man: Brand New Day." The system retrieves and displays the available showtimes for the selected movie. The customer selects a preferred showtime and specifies the number of tickets to purchase. The system checks whether the requested number of seats is available. If sufficient seats are unavailable, the system notifies the customer that the requested number of seats cannot be reserved, and the booking process ends. If the seats are available, the system calculates the total ticket price and requests payment from the customer. The payment is then processed. If the payment is unsuccessful, the system notifies the customer that the payment has failed, and the booking process ends. If the payment is successful, the system creates the movie ticket, sends a booking confirmation to the customer, and completes the ticket booking process.
Explanation: This sequence diagram models synchronous interactions flowing from the Customer to the System. A nested alt fragment handles the seat availability logic and the subsequent payment success/failure logic.
Note: Activation bars (Execution Specifications) have been omitted from this diagram code to ensure strict rendering compatibility. When drawing your final assignment, please ensure you manually add the activation bars to the lifelines to show exactly when the System is actively processing requests.

            end

Exercise 2: ATM Cash Withdrawal System

Question: An ATM system allows customers to withdraw cash from their bank accounts. A customer inserts an ATM card into the machine. The ATM sends the card details to the bank server for verification. If the card is invalid, the ATM rejects the card and terminates the transaction. If the card is valid, the ATM prompts the customer to enter the PIN. The ATM forwards the entered PIN to the bank server for verification. If the PIN is incorrect, the ATM rejects the transaction and ejects the card. If the PIN is verified successfully, the ATM prompts the customer to enter the withdrawal amount. The ATM sends the withdrawal request to the bank server. The bank server checks the account balance. If sufficient funds are available, the bank server deducts the requested amount from the customer's bank account and notifies the ATM that the transaction is successful. The ATM dispenses the cash and ejects the card. If there are insufficient funds, the bank server notifies the ATM that the transaction has failed. The ATM displays an insufficient funds message and ejects the card.
Explanation: This diagram is highly nested because of the multiple sequential validation steps (Card, PIN, Funds). Notice how the ATM acts as an intermediary between the Customer and the Bank Server.
Note: Activation bars (Execution Specifications) have been omitted from this diagram code to ensure strict rendering compatibility. When drawing your final assignment, please ensure you manually add the activation bars correctly to the ATM and BankServer lifelines to show when they are actively processing data. 
        sequenceDiagram
            actor Customer
            participant ATM
            participant BankServer
            
            Customer->>ATM: Insert ATM Card
            ATM->>BankServer: Verify Card Details
            
            alt Card Invalid
                BankServer-->>ATM: Card Invalid
                ATM-->>Customer: Reject Card & Terminate
            else Card Valid
                BankServer-->>ATM: Card Valid
                ATM-->>Customer: Prompt for PIN
                
                Customer->>ATM: Enter PIN
                ATM->>BankServer: Verify PIN
                
                alt PIN Incorrect
                    BankServer-->>ATM: PIN Incorrect
                    ATM-->>Customer: Reject Transaction & Eject Card
                else PIN Correct
                    BankServer-->>ATM: PIN Verified
                    ATM-->>Customer: Prompt for Withdrawal Amount
                    
                    Customer->>ATM: Enter Amount
                    ATM->>BankServer: Withdrawal Request
                    BankServer->>BankServer: Check Account Balance
                    
                    alt Insufficient Funds
                        BankServer-->>ATM: Transaction Failed
                        ATM-->>Customer: Display Insufficient Funds & Eject Card
                    else Sufficient Funds
                        BankServer->>BankServer: Deduct Amount
                        BankServer-->>ATM: Transaction Successful
                        ATM-->>Customer: Dispense Cash & Eject Card
                    end
                end
            end

4. Lab 04: Class Diagrams

Complete UML Conventions & Symbols (Class Diagrams):
  • Class Box: Three compartments: Name (top), Attributes (middle), Operations (bottom). + Public, - Private.
  • Inheritance/Generalization: Solid line with hollow triangle. Represents an "is-a" relationship.
  • Realization/Implementation: Dashed line with hollow triangle. Used for implementing interfaces.
  • Aggregation: Solid line with a hollow diamond. Represents a "has-a" relationship where the child can exist independently.
  • Composition: Solid line with a filled diamond. Represents a strict "owns-a" relationship (lifecycle dependency).
  • Association: Solid line connecting two classes indicating they communicate or are linked.
  • Dependency: Dashed line with open arrow. Changes in one element may affect the other.

Exercise 3: University Management System

Question: A university manages students, lecturers, departments, courses, enrolments, assignments, submissions, and grades. Every Person has a name, address, email, and phone number. A Student and a Lecturer are specialized types of Person and have unique identifiers: studentID and lecturerID, respectively. Each department has a department ID, name, and office location. A department employs multiple lecturers and offers multiple courses. Each lecturer belongs to exactly one department. Each course has a course code, title, number of credits, and semester. A lecturer may teach multiple courses, while each course is taught by one lecturer. Students enroll in courses. The enrolment records the enrolment date and current status. Each course contains multiple assignments. Every assignment has a title, description, due date, and total marks. Students submit assignments. A submission stores the submission date, obtained marks, and feedback.
Explanation: This diagram models static structures. `Student` and `Lecturer` inherit from a generalized `Person` class to reuse attributes. A `Department` aggregates `Lecturers` and `Courses` (because departments don't strictly "own" the lifecycle of a person, though course aggregation is debatable, composition is used here for standard academic modeling). `Enrolment` serves as an association class resolving the many-to-many relationship between `Student` and `Course` because it holds data (status, date) specific to the relationship.
Assumptions: The relationship between Student and Course is many-to-many. Because "Enrolment" holds data (date, status) specifically about that many-to-many link, it is logically an Association Class.

            }

              -String departmentID
              -String name
              -String officeLocation
            }
            
            class Course {
              -String courseCode
              -String title
              -int credits
              -int semester
            }
            
            class Enrolment {

              -String status
            }

Exercise 4: Vehicle System

Question: A vehicle management system keeps records of vehicles and their engines. Each vehicle has a unique vehicle number, model, and manufacturer. A vehicle can be powered by either a PetrolEngine or an Electric Engine. Every engine has an engine ID and is responsible for starting the vehicle. Although both engine types provide the ability to start a vehicle, the procedure for starting the engine differs depending on the engine type. The system stores information about the engine installed in each vehicle so that the appropriate engine can be used whenever the vehicle is started.
Explanation: This demonstrates inheritance and polymorphism. The abstract `Engine` class defines the `start()` operation. `PetrolEngine` and `ElectricEngine` inherit from it to provide specific implementations. A `Vehicle` is composed of exactly one generic `Engine`, enabling it to start regardless of the underlying engine type. *(Note: The HTML-safe entity for the inheritance arrow `<|--` is explicitly used to ensure strict syntax rendering).* 
        classDiagram
            class Vehicle {
              -String vehicleNumber
              -String model
              -String manufacturer
              +startVehicle() void
            }
            
            class Engine {
              -String engineID
              +start() void
            }
            
            class PetrolEngine {
              +start() void
            }
            
            class ElectricEngine {
              +start() void
            }
            
            Vehicle "1" *-- "1" Engine : powered by
            
            Engine <|-- PetrolEngine
            Engine <|-- ElectricEngine
