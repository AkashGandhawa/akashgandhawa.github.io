UML Analysis and Design: Theory Guide

A comprehensive visual guide covering the theoretical conventions, symbols, and practical examples for all 8 specified UML diagram types.

Rendering Note: The diagrams below are dynamically rendered using Mermaid.js with strictly corrected syntax. Activation bars in sequence diagrams have been omitted from the raw code to guarantee rendering stability across all browsers, but their required placement is detailed in the explanations.

1. Use Case Diagram

Complete UML Conventions & Symbols

  • Actor: External entity interacting with the system.
  • System Boundary: Box defining the scope of the system.
  • Use Case: Represents a functional requirement.
  • Association: Solid line connecting an Actor to a Use Case.
  • <<include>> / <<extend>>: Dashed arrow showing dependency.

Example: Online Banking System

Description: You have been hired to build an Online Banking System. The system allows customers to log in, view their account balance, transfer money, and pay bills. If a transfer exceeds a daily limit, the system sends an alert to the customer. Bank staff can view customer accounts and generate financial reports. The system automatically generates a daily transaction summary every midnight. Transfer Money and Pay Bill both require the user to be logged in. When a transfer exceeds the daily limit, the system sends an alert. "Verify Password" is always required during Login. Draw ALL the relationships between these elements.

Explanation

  • Actors: The primary actors are the Customer and Bank Staff, who possess goals fulfilled by the system. A secondary actor is the automated timer/system triggering the midnight summary.
  • Relationships: Because "Transfer Money" and "Pay Bill" mandate logging in, they are connected to "Login" using an <<include>> relationship.
  • "Verify Password" is a mandatory component of logging in, thus it is an included use case of "Login".
  • Sending an alert only happens under specific limits, so it is modeled using an <<extend>> relationship branching off "Transfer Money".

2. Activity Diagram

Complete UML Conventions & Symbols

  • Initial Node: Filled circle. Start of the workflow.
  • Action/Activity: Represents a single step.
  • Decision / Merge Node: Diamond shape representing splits or joins in logic.
  • Fork/Join Node: Splits (Fork) or syncs (Join) concurrent threads.
  • Swimlanes: Divides diagram to show who is responsible for actions.
  • Final Node: Bullseye marking the end.

Example: Maintaining Storage Tanks

Description: First the Gardner examines the levels of the storage tanks' contents. If he determines that tanks need to be refilled, he should initiate the refilling process. In such case, Gardner will first suspend the normal hydroponics system operation of storage tanks. Then he will select tanks and sets fill levels. Next, he will fill the tanks. If tank is heated, the system disables heaters before filling and enables them after. Finally, the Gardner will resume the normal hydroponics system operation.

Explanation

  • Swimlanes partition the responsibilities between the Gardener, the WaterTank, and the NutrientTank.
  • The process splits into parallel operations for disabling the heating, filling the water tank, and filling the nutrient tank.
  • A Fork node handles the simultaneous split into the tank elements, and a Join node awaits the completion of all filling tasks before allowing the system to resume operations.
        stateDiagram-v2
            [*] --> CheckLevels
            
            state Gardener {
                CheckLevels : Check Tank Levels
                Suspend : Suspend Operations
                SetLevels : Set Fill Levels
                Resume : Resume Operations
            }
            
            state WaterTank {
                DisableHeat : Disable Heating
                FillWater : Fill
                EnableHeat : Enable Heating
            }
            
            state NutrientTank {
                FillNutrient : Fill
            }
            
            CheckLevels --> if_levels
            state if_levels <<choice>>
            if_levels --> Suspend : [needs refill]
            if_levels --> [*] : [all levels within tolerance]
            
            Suspend --> SetLevels : [suspended]
            
            state fork_fill <<fork>>
            SetLevels --> fork_fill
            
            fork_fill --> DisableHeat
            fork_fill --> FillNutrient
            
            DisableHeat --> FillWater : [heater below safe temp]
            FillWater --> EnableHeat : [full]
            
            state join_fill <<join>>
            EnableHeat --> join_fill
            FillNutrient --> join_fill : [full]
            
            join_fill --> Resume
            Resume --> [*]

3. Sequence Diagram

Complete UML Conventions & Symbols

  • Lifeline: Represents an object's existence over time.
  • Synchronous Message: Sender waits for a response.
  • Asynchronous Message: Sender does not wait.
  • Return Message: Dashed line indicating a reply.
  • Combined Fragment: Frame for conditional logic or loops.

Example: Maintaining the Climatic Plan

Description: There are four entities involved for maintaining a climatic plan. The "Gardening Planner" is responsible for maintaining the climatic plan. The "Environment Planner" sets the optimal environmental parameters. To maintain the optimal temperature, the Environment planner iteratively checks the current temperature. If the observed temperature is below the optimal level, it'll increase the temperature by invoking the heating functionality of the "Heater" entity. Else if the observed temperature is above the optimal level, the environment controller will invoke the cooling functionality of the "Cooler" entity to reduce the temperature.

Explanation

  • The loop fragment manages the iterative checking of the temperature.
  • Inside the loop, an alt combined fragment controls the branching conditional logic based on the temperature parameter.
  • If the temperature is too low, a synchronous message is sent to the Heater object.
  • If the temperature is too high, a message is routed to the Cooler object instead.
        sequenceDiagram
            participant GP as :GardeningPlan
            participant EC as :EnvironmentController
            participant H as :Heater
            participant C as :Cooler
            
            GP->>EC: setClimate
            
            loop Continuous Maintenance
                EC->>EC: Determine current temperature
                
                alt Temperature too low
                    EC->>H: heat
                else Temperature too high
                    EC->>C: cool
                end
                
                EC->>GP: Log the climate change
            end

4. Class Diagram

Complete UML Conventions & Symbols

  • Class Box: Three compartments: Name, Attributes, Operations.
  • Inheritance: Represents an "is-a" relationship.
  • Aggregation: Represents a loosely-coupled "has-a" relationship.
  • Composition: Strong "owns-a" lifecycle dependency.
  • Association: Indicates classes communicate or are linked.

Example: Drawing Application

Description: Shape is an abstract class. Circle, Rectangle and Polygon are derived from Shape. There is an association between DialogBox and DataController. Shape is part-of Window (Aggregation). Point is part-of Circle (Composition). Window is dependent on Event. The attributes of Circle are radius and center. The method names of Circle are area(), circum(), setCenter() and setRadius().

Explanation

  • Shape is modeled as the generalized superclass for Circle, Rectangle, and Polygon.
  • The aggregation between Window and Shape indicates shapes exist within a window but can logically persist independently.
  • The composition between Circle and Point guarantees that if the circle is deleted, its central point data is also destroyed.

5. Object Diagram

Theory & Conventions

  • An object diagram captures the static view of a system at a particular moment in time, representing a concrete instance.
  • Objects are formatted as Object name : Class name.
  • Links connect objects to map their concrete relationships matching the abstract class associations.
  • It helps to understand object behavior and data values from a practical, instantiated perspective.

Example: Order Management System Instances

Description: Now the customer object (C) is associated with three order objects (O1, O2, and O3). These order objects are associated with special order and normal order objects (S1, S2, and N1). The customer has the following three orders with different numbers (12, 32 and 40) for the particular time considered.

Explanation

  • This object diagram displays a snapshot of instances derived from an abstract Order Management class hierarchy.
  • Instead of showing that a customer can have many orders, it explicitly shows c: Customer connected to exactly three instantiated order objects.
  • The attributes reflect the exact state values at the time of the snapshot, such as the specific order numbers 12, 32, and 40.

6. State Diagram

Complete UML Conventions & Symbols

  • State: Represents a condition satisfying a specific situation.
  • Initial State: Where the object's lifecycle begins.
  • Transition: Triggered by an event to move between states.
  • Final State: Where the lifecycle ends.

Example: Heater System

Description: State Machine Diagrams are often used for deriving testing cases. The heater has Idle, Heating, Cooling (Startup, Ready, Running), and Failure states. Transitions trigger based on "too hot", "too cool", "compressor running", "ok", and "failure" events.

Explanation

  • The Cooling state is modeled as a composite state encompassing Startup, Ready, and Running substates.
  • This simplifies the architecture because a single failure event arrow can be drawn exiting the boundary of the composite state.
  • Events dictate the transition conditions directly between states.
        stateDiagram-v2
            [*] --> Idle
            
            state Cooling {
                [*] --> Startup
                Startup --> Ready : compressor running
                Ready --> Running : fan running
            }
            
            Idle --> Heating : too cool
            Heating --> Idle : ok
            Heating --> Failure : failure
            
            Idle --> Cooling : too hot
            Cooling --> Idle : ok
            Cooling --> Failure : failure
            
            Failure --> Idle : failure cleared

7. Component Diagram

Complete UML Conventions & Symbols

  • Component: Autonomous modular unit with hidden internals.
  • Provided Interface: Services offered to the environment.
  • Required Interface: Services expected from the environment.

Example: Online Shopping System

Description: Visualize the software components and their dependencies to each other in an Online Shopping System containing Product, Order, Customer, Payment, and Account components linked via usage interfaces.

Explanation

  • Component diagrams focus on Service-Oriented Architecture (SOA) and modularity rather than class structures.
  • The Order component requires services from Product, Customer, and Payment components to successfully complete its aggregate tasks.
  • The Payment component acts as an autonomous module, requiring data validation services specifically provided by the Account module.

8. Package Diagram

Complete UML Conventions & Symbols

  • Package: Groups elements and provides a namespace.
  • Dependency: A dashed arrow indicating a reliance on another element.

Example: Order Processing System Layering

Description: We are going to design a package diagram for a "Track Order" scenario for an online shopping store. Track Order module is responsible for providing tracking information. It gets order details from "Order Processing". Next, it has to know about shipping details, let us call that "Shipping". Track order should get order details from "Order Processing" and "Order Processing" has to know the tracking info given by the customer. "Shipping" can import "Track Order" to make the navigation easier. Finally, Track Order dependency to UI Framework is mapped.

Explanation

  • Packages provide high-level boundaries for system modules.
  • Dual <<access>> dependencies are used between Track Order and Order Processing because the modules are securely sharing encapsulated data back and forth.
  • The Shipping package utilizes an <<import>> dependency to publicly incorporate the tracking elements required to update transit locations.
        flowchart LR
            UIFramework["📦 UI Framework"]
            OrderProcessing["📦 Order Processing"]
            TrackOrder["📦 Track Order"]
            Shipping["📦 Shipping"]
            
            UIFramework -.->|<<access>>| TrackOrder
            TrackOrder -.->|<<access>>| OrderProcessing
            OrderProcessing -.->|<<access>>| TrackOrder
            Shipping -.->|<<import>>| TrackOrder
